It is very smart and very fast at doing one task after another. Most CPUs today have a few cores, let&#x27;s say 4, 8, or 16. A core is one unit that can do one thing at a time.</p><p>A <strong>GPU</strong> (Graphics Processing Unit) is a different kind of chip. It was originally built to draw pictures on the screen. Drawing a picture means calculating the color of millions of tiny dots called pixels, and the good thing is that each dot can be calculated separately, without waiting for the others. So, a GPU was designed to have thousands of small cores that all work at the same time. Working on many things at the same time is called working in <strong>parallel</strong>.</p><p>Let&#x27;s say we have a big kitchen and we need to peel 10,000 potatoes.</p><ul><li>A CPU is like one master chef. The master chef is very skilled and very fast, but can peel only one potato at a time.</li><li>A GPU is like 5,000 helpers. Each helper is slower than the master chef, but all 5,000 of them peel potatoes at the same time.</li></ul><p>For peeling 10,000 potatoes, the 5,000 helpers will win easily.</p><p>Now, think about AI. Training or running an AI model means doing millions of small multiplications and additions. And most of these calculations do not depend on each other. This is exactly the &quot;peeling potatoes&quot; kind of work. So, here comes the GPU to the rescue.</p><p><strong>But, here is the catch.</strong> A GPU cannot decide on its own what to do. Someone has to write a program that tells all those thousands of small cores what work to do. This is where CUDA comes into the picture.</p><h2 id="what-is-cuda"><a href="#what-is-cuda" aria-hidden="true" tabindex="-1"></a>What is CUDA?</h2><p><strong>CUDA (Compute Unified Device Architecture)</strong> is a platform created by NVIDIA, the company that makes most of the GPUs used for AI, that lets us write programs that run on the GPU.</p><p>In simple words, CUDA is a way to write normal-looking code, in languages like C, C++, Python and etc., and make it run on thousands of GPU cores at the same time.</p><p>Before CUDA, if we wanted to use a GPU for something other than graphics, we had to trick the GPU by pretending our data was a picture. That was very painful. We needed a solution for that, and CUDA was introduced to solve this problem. With CUDA, we can directly tell the GPU: &quot;Here is my data, here is the work, do it in parallel.&quot;</p><p>Now, the question is, how do we tell the GPU what work to do? The answer is: by writing a <strong>kernel</strong>.</p><h2 id="what-is-a-cuda-kernel"><a href="#what-is-a-cuda-kernel" aria-hidden="true" tabindex="-1"></a>What is a CUDA Kernel?</h2><p><strong>A CUDA Kernel is a function that runs on the GPU, and it is executed by many threads at the same time.</strong></p><p>Let&#x27;s break this down.</p><p>A <strong>function</strong> is just a piece of code that does one job. We must be knowing this from any programming language.</p><p>A <strong>thread</strong> is one worker that runs the code. In simple words, a thread is one helper from our kitchen example.</p><p>So, CUDA Kernel = Function + Runs on GPU + Executed by thousands of threads together.</p><p>Here is the most important idea, and I want you to remember this:</p><p><strong>We write the kernel once, as if it is for a single thread. Then the GPU runs that same kernel thousands of times in parallel, once per thread.</strong></p><p>Let&#x27;s go back to the kitchen. We do not write 5,000 different instructions for 5,000 helpers. We write one instruction: &quot;Pick up a potato and peel it.&quot; Then all 5,000 helpers follow the same instruction at the same time. The only difference is, each helper picks up a different potato.</p><p>That is exactly how a CUDA Kernel works. One instruction, thousands of workers, and each worker handles a different piece of data.</p><p>Now, we have understood what a CUDA Kernel is.</p><h2 id="threads-blocks-and-grids"><a href="#threads-blocks-and-grids" aria-hidden="true" tabindex="-1"></a>Threads, Blocks, and Grids</h2><p>Now, if we have thousands of threads, we need some way to organize them. Otherwise, it will be a mess. CUDA organizes threads in three levels.</p><ul><li><strong>Thread:</strong> A single worker. It runs the kernel code once.</li><li><strong>Block:</strong> A group of threads. Let&#x27;s say 256 threads in one block. Threads inside the same block can talk to each other and share a small amount of memory.</li><li><strong>Grid:</strong> A group of blocks. All the blocks together make up one kernel launch.</li></ul><p>So, Grid = Many Blocks, and Block = Many Threads.</p><p>Let&#x27;s understand this with our kitchen.</p><ul><li>A thread is one helper.</li><li>A block is one team of helpers standing at one table. They can pass things to each other easily because they are at the same table.</li><li>A grid is the whole kitchen with all the tables.</li></ul><p>When we launch a kernel, we tell CUDA two things: how many blocks we want, and how many threads we want in each block. CUDA then creates all those threads and runs the kernel on each one.</p><p><strong>Note:</strong> There is a limit on how many threads can be in one block, usually 1024. That is why we use many blocks. There is no practical limit on the number of blocks, so we can have millions of threads in total.</p><p>Now that we have learned how threads are organized, it&#x27;s time to learn how the CPU and the GPU talk to each other.</p><h2 id="host-and-device"><a href="#host-and-device" aria-hidden="true" tabindex="-1"></a>Host and Device</h2><p>Before writing the code, we need to understand two words that we will see everywhere in CUDA.</p><ul><li><strong>Host:</strong> The CPU and its memory (RAM, the main memory of the computer).</li><li><strong>Device:</strong> The GPU and its own memory (VRAM, the memory that sits on the graphics card itself).</li></ul><p>The host and the device have separate memory. For the sake of understanding, assume that the CPU cannot directly read the GPU memory, and the GPU cannot directly read the CPU memory. So, whenever we want the GPU to work on some data, we must copy that data from the host to the device. And when the work is done, we must copy the result back from the device to the host.</p><p>Means, a CUDA program always follows these steps:</p><p><strong>Step 1:</strong> Prepare the data on the host (CPU).</p><p><strong>Step 2:</strong> Allocate memory on the device (GPU). Allocate just means reserve some space for our data.</p><p><strong>Step 3:</strong> Copy the data from host to device.</p><p><strong>Step 4:</strong> Launch the kernel on the device.</p><p><strong>Step 5:</strong> Copy the result from device back to host.</p><p><strong>Step 6:</strong> Free the device memory, which means give the reserved space back.</p><p>Think of it like this. The master chef (CPU) has all the potatoes in the store room. The helpers (GPU) work in a different room. So, the chef must carry the potatoes to the helpers&#x27; room, let them peel, and then carry the peeled potatoes back. The carrying takes time, and we will see later why this matters.</p><p><strong>Planning your move into AI?</strong></p><p>No matter which tech domain you work in today, with your effort, you can transition to these roles:</p><ul><li>AI Engineer</li><li>Forward Deployed Engineer</li><li>AI Agent Engineer</li><li>Harness Engineer</li><li>Voice AI Engineer</li><li>AI Architect</li><li>LLM Engineer</li><li>LLM Inference Engineer</li><li>Gen AI Engineer</li><li>MLOps Engineer</li><li>ML Engineer</li><li>Deep Learning Engineer</li></ul><p>Our <a target="_blank" rel="noopener noreferrer" href="https://outcomeschool.com/program/ai-and-machine-learning">AI and Machine Learning Program</a> at Outcome School takes you there.</p><h2 id="writing-our-first-cuda-kernel"><a href="#writing-our-first-cuda-kernel" aria-hidden="true" tabindex="-1"></a>Writing our first CUDA Kernel</h2><p>The best way to learn this is by taking an example.</p><p>Let&#x27;s say we have two lists of numbers, <code>a</code> and <code>b</code>, each with one million numbers. We want to add them and store the result in a third list <code>c</code>. Means, <code>c[i] = a[i] + b[i]</code> for every position <code>i</code>.</p><p>First, let&#x27;s see how we do this on a CPU without CUDA:</p><div class="relative"><pre><code class="language-c code-highlight">void add(int n, float *a, float *b, float *c) {
    for (int i = 0; i &lt; n; i++) {
        c[i] = a[i] + b[i];
    }
}
</code></pre></div><p>Here, we have a function named <code>add</code>. The word <code>void</code> means the function does not return anything. <code>float</code> means a number with a decimal point, and <code>float *a</code> means a list of such numbers. Inside, we have a loop that goes from <code>0</code> to <code>n - 1</code>. In each step, it adds one pair of numbers. For one million numbers, this loop runs one million times, one after another. One master chef, one potato at a time.</p><p>Now, let&#x27;s see the same thing as a CUDA Kernel:</p><div class="relative"><pre><code class="language-c code-highlight">__global__ void add(int n, float *a, float *b, float *c) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i &lt; n) {
        c[i] = a[i] + b[i];
    }
}
</code></pre></div><p>Here, we can notice a few things:</p><ul><li><code>__global__</code> is a special keyword. It tells CUDA that this function is a kernel. It will be called from the host (CPU) and will run on the device (GPU).</li><li>One more thing to notice, <strong>the loop is gone.</strong> There is no <code>for</code> loop anymore. Each thread handles only one <code>i</code>. The GPU will run this function one million times in parallel, once for each thread, and each thread will take care of one position.</li><li><code>int i = blockIdx.x * blockDim.x + threadIdx.x;</code> is how each thread finds out which <code>i</code> it is responsible for. Do not worry, we will understand this line in detail in the next section.</li><li><code>if (i &lt; n)</code> is a safety check. Sometimes we launch a few more threads than the number of items. This check makes sure the extra threads do nothing.</li></ul><p>This is the whole kernel. Just a few lines. And it does the work of one million loop iterations at once.</p><p>Now, let&#x27;s see how we launch this kernel from the host (CPU):</p><div class="relative"><pre><code class="language-c code-highlight">int n = 1000000;
int threadsPerBlock = 256;
int blocks = (n + threadsPerBlock - 1) / threadsPerBlock;

add&lt;&lt;&lt;blocks, threadsPerBlock&gt;&gt;&gt;(n, d_a, d_b, d_c);
</code></pre></div><p>Here, we have:</p><ul><li><code>threadsPerBlock = 256</code> means each block will have 256 threads.</li><li><code>blocks = (n + threadsPerBlock - 1) / threadsPerBlock</code> calculates how many blocks we need to cover all one million numbers. This formula is just a trick to round up. For one million numbers and 256 threads per block, we get 3907 blocks. 3907 multiplied by 256 gives 1,000,192 threads, which is a little more than one million. That is why we needed the <code>if (i &lt; n)</code> check inside the kernel.</li><li><code>&lt;&lt;&lt;blocks, threadsPerBlock&gt;&gt;&gt;</code> is the special CUDA syntax for launching a kernel. The three angle brackets tell CUDA: &quot;Run this function with this many blocks and this many threads per block.&quot;</li><li><code>d_a</code>, <code>d_b</code>, <code>d_c</code> are the addresses of our data in the device memory. In simple words, they tell the kernel where the data lives on the GPU. The <code>d_</code> prefix is just a naming convention that means &quot;device&quot;. We copied our data there before calling the kernel.</li></ul><p>Let&#x27;s see the complete flow with the memory steps we discussed earlier:</p><div class="relative"><pre><code class="language-c code-highlight">// Step 1: a, b, and c are already prepared on the host

// Step 2: Allocate memory on the device
float *d_a, *d_b, *d_c;
cudaMalloc(&amp;d_a, n * sizeof(float));
cudaMalloc(&amp;d_b, n * sizeof(float));
cudaMalloc(&amp;d_c, n * sizeof(float));

// Step 3: Copy data from host to device
cudaMemcpy(d_a, a, n * sizeof(float), cudaMemcpyHostToDevice);
cudaMemcpy(d_b, b, n * sizeof(float), cudaMemcpyHostToDevice);

// Step 4: Launch the kernel
add&lt;&lt;&lt;blocks, threadsPerBlock&gt;&gt;&gt;(n, d_a, d_b, d_c);

// Step 5: Copy result from device to host
cudaMemcpy(c, d_c, n * sizeof(float), cudaMemcpyDeviceToHost);

// Step 6: Free the device memory
cudaFree(d_a);
cudaFree(d_b);
cudaFree(d_c);
</code></pre></div><p>Here, we have:</p><ul><li><code>cudaMalloc</code> reserves space in the GPU memory. In simple words, it tells the GPU: &quot;Keep this much space ready for my data.&quot;</li><li><code>cudaMemcpy</code> copies data between host and device. The last argument tells the direction: <code>cudaMemcpyHostToDevice</code> or <code>cudaMemcpyDeviceToHost</code>.</li><li>The kernel launch line is the same as before.</li><li><code>cudaFree</code> releases the GPU memory once we are done.</li></ul><p>It works perfectly. All one million additions are done in parallel by the GPU.</p><p><strong>Note:</strong> CUDA code is saved in a file with the <code>.cu</code> extension and compiled using a special tool from NVIDIA called <code>nvcc</code>. It understands both the normal C++ code for the host and the kernel code for the device.</p><p><strong>A quick note for you</strong></p><p>No matter which tech domain you work in, get familiar with these topics:</p><ul><li>LLM</li><li>RAG</li><li>MCP</li><li>Agent</li><li>Fine-tuning</li><li>Quantization</li></ul><p>We put it all together in one video:</p><p><a target="_blank" rel="noopener noreferrer" href="https://www.youtube.com/watch?v=lnfWvX66FUk">AI Engineering Explained: LLM, RAG, MCP, Agent, Fine-Tuning, and Quantization</a></p><p>No need to stop reading - bookmark it and watch later when you get time. Future you will thank you.</p><p>Now, let&#x27;s get back to the topic.</p><h2 id="how-a-thread-finds-its-own-work"><a href="#how-a-thread-finds-its-own-work" aria-hidden="true" tabindex="-1"></a>How a thread finds its own work</h2><p>Now, let&#x27;s understand the most important line in our kernel:</p><div class="relative"><pre><code class="language-c code-highlight">int i = blockIdx.x * blockDim.x + threadIdx.x;
</code></pre></div><p>Remember, every thread runs the exact same code. So, how does each thread know which number to add? The answer is: CUDA gives every thread some built-in variables that tell it where it is. These variables are called indexes, and index just means the position number, starting from 0.</p><ul><li><code>threadIdx.x</code> is the index of the thread inside its block. If a block has 256 threads, this goes from <code>0</code> to <code>255</code>.</li><li><code>blockIdx.x</code> is the index of the block inside the grid. If we have 3907 blocks, this goes from <code>0</code> to <code>3906</code>.</li><li><code>blockDim.x</code> is the number of threads in each block. In our case, it is <code>256</code>.</li></ul><p>So, the global index <code>i</code> is calculated as below:</p><p><code>i = (block number) * (threads per block) + (thread number inside the block)</code></p><p>Let&#x27;s take an example for the sake of understanding.</p><ul><li>Thread 0 in Block 0: <code>i = 0 * 256 + 0 = 0</code></li><li>Thread 5 in Block 0: <code>i = 0 * 256 + 5 = 5</code></li><li>Thread 0 in Block 1: <code>i = 1 * 256 + 0 = 256</code></li><li>Thread 10 in Block 2: <code>i = 2 * 256 + 10 = 522</code></li></ul><p>Every thread gets a unique <code>i</code>, and no two threads get the same <code>i</code>. This is how the same code, running on thousands of threads, works on different data.</p><p>Let&#x27;s go back to the kitchen one last time. Every helper has a table number (<code>blockIdx</code>) and a seat number at that table (<code>threadIdx</code>). Each table has 256 seats (<code>blockDim</code>). So, a helper at table 2, seat 10 knows that the potato to pick is number 522. The helper does not need to ask anyone. The helper just calculates it and picks up potato number 522.</p><p><strong>Note:</strong> We used <code>.x</code> everywhere because CUDA allows threads and blocks to be arranged in one dimension (like a line), two dimensions (like a grid on paper), or three dimensions (like a cube). For a simple list, one dimension is enough. For an image or a matrix, two dimensions are natural, and we would also use <code>.y</code>. The idea remains the same.</p><p>Now, we have understood how a thread finds its own work.</p><h2 id="what-happens-inside-the-gpu-when-a-kernel-runs"><a href="#what-happens-inside-the-gpu-when-a-kernel-runs" aria-hidden="true" tabindex="-1"></a>What happens inside the GPU when a kernel runs</h2><p>Till now, we have learned how to write and launch a kernel. Now, let&#x27;s see what the GPU actually does with it.</p><p>A GPU is made of many <strong>Streaming Multiprocessors (SMs)</strong>. In simple words, an SM is one big work unit inside the GPU that contains many small cores. A modern GPU can have more than 100 SMs.</p><p>When we launch a kernel with 3907 blocks, CUDA does not run all of them at once. It distributes the blocks to the SMs. Each SM takes a few blocks, finishes them, and then takes the next few. This continues until all the blocks are done.</p><p>Inside an SM, threads do not run one by one either. The SM groups threads into bunches of 32, and this bunch is called a <strong>warp</strong>. All 32 threads in a warp execute the same instruction at the same moment. That is why CUDA is so fast. One instruction is fetched once and applied to 32 threads together.</p><p>Let&#x27;s connect this to our kitchen. The kitchen (GPU) is divided into many sections (SMs). Each section handles a few tables (blocks) at a time. At every table, the helpers (threads) are organized in rows of 32 (warps). The head of the table says one instruction, &quot;peel&quot;, and all 32 helpers in a row do it together.</p><p><strong>But, here is the catch.</strong> Because all 32 threads in a warp must run the same instruction, if our kernel has an <code>if</code> condition and some threads go one way and some go the other way, the warp has to run both paths one after another. This is called <strong>warp divergence</strong>, and it slows things down. That is why good CUDA kernels try to keep the threads doing the same thing as much as possible.</p><p><strong>Note:</strong> Our <code>if (i &lt; n)</code> check causes divergence only in the very last block, so it is not a problem in practice.</p><p>To learn LLM Inference Engineering and LLM Inference Bottleneck Analysis, which build directly on how the GPU runs our work, check out our <a target="_blank" rel="noopener noreferrer" href="https://outcomeschool.com/program/ai-and-machine-learning">AI and Machine Learning Program</a> at Outcome School.</p><h2 id="memory-in-cuda"><a href="#memory-in-cuda" aria-hidden="true" tabindex="-1"></a>Memory in CUDA</h2><p>We have already seen that the host and device have separate memory. Now, let&#x27;s look inside the device memory, because this is where most of the performance comes from.</p><p>There are three main types of memory in a GPU that we must know about:</p><ul><li><strong>Global Memory:</strong> This is the big memory of the GPU (the VRAM, let&#x27;s say 24 GB or 80 GB). All threads can read and write it. This is where <code>d_a</code>, <code>d_b</code>, and <code>d_c</code> live. It is large but slow, because it is far from the cores.</li><li><strong>Shared Memory:</strong> This is a small, very fast memory inside each SM. Only the threads of the same block can use it. It is like a whiteboard at each table that all helpers at that table can see and write on.</li><li><strong>Registers:</strong> These are the fastest memory of all, and each thread gets its own. Our variable <code>i</code> lives in a register. It is like the notepad in each helper&#x27;s hand.</li></ul><p>Global memory is around 100 times slower than shared memory. So, a common trick in CUDA programming is: load a chunk of data from global memory into shared memory once, let all the threads in the block work on it many times from shared memory, and then write the result back to global memory.</p><p>For our simple addition example, each number is used only once, so shared memory does not help. But for <a target="_blank" rel="noopener noreferrer" href="matrix-multiplication-in-neural-networks.md">matrix multiplication</a> (multiplying large tables of numbers, which we will see in the next section), where the same numbers are used again and again, this trick makes a huge difference. We have a detailed blog on <a target="_blank" rel="noopener noreferrer" href="decoding-flash-attention.md">Flash Attention</a> that explains how this exact trick makes attention in LLMs much faster.</p><p><strong>Stay updated:</strong> Subscribe to our <a target="_blank" rel="noopener noreferrer" href="https://outcomeschool.substack.com/subscribe">newsletter</a> to get our latest AI and Machine Learning blogs straight to your inbox.</p><p>This was all about the memory in CUDA. Now, let&#x27;s connect all of this to AI.</p><h2 id="why-cuda-kernels-matter-for-ai"><a href="#why-cuda-kernels-matter-for-ai" aria-hidden="true" tabindex="-1"></a>Why CUDA Kernels matter for AI</h2><p>An AI model, like an LLM (Large Language Model, the kind of model behind ChatGPT), is basically a very large collection of numbers called weights. When we give it an input, the model multiplies the input with those weights, adds them up, applies a few simple mathematical functions, and repeats this many times across many layers. Almost everything inside an AI model is <strong>matrix multiplication</strong>, which means multiplying and adding large tables of numbers.</p><p>A matrix multiplication with millions of numbers is the perfect &quot;peeling potatoes&quot; problem. Every output number can be calculated independently. So, we write one CUDA kernel for matrix multiplication and launch it with millions of threads.</p><p>When we use a library like <a target="_blank" rel="noopener noreferrer" href="how-does-pytorch-work.md">PyTorch</a> (a popular tool for building AI models) and write <code>torch.matmul(a, b)</code>, we are not writing any CUDA code ourselves. But behind the scenes, PyTorch calls a highly optimized CUDA kernel written by NVIDIA. These kernels come from NVIDIA libraries like cuBLAS, which is a collection of ready-made kernels for math operations. They do exactly what we learned today, but with many more tricks for speed. We have a detailed blog on <a target="_blank" rel="noopener noreferrer" href="how-does-tensorrt-llm-work.md">how TensorRT-LLM works</a> that covers how NVIDIA fuses and tunes these kernels to run an LLM as fast as possible.</p><p>So, every time an LLM generates a word, thousands of CUDA kernels are launched on the GPU, one after another. Every step inside the model, whether it is a big matrix multiplication or a small mathematical function, is a CUDA kernel. This is why we cannot imagine modern AI without GPUs and CUDA.</p><p>If we want to go deep into PyTorch and the math inside an LLM, and build a Large Language Model (LLM) from scratch, our <a target="_blank" rel="noopener noreferrer" href="https://outcomeschool.com/program/ai-and-machine-learning">AI and Machine Learning Program</a> at Outcome School covers it end to end.</p><h2 id="where-cuda-kernels-work-well-and-where-they-fail"><a href="#where-cuda-kernels-work-well-and-where-they-fail" aria-hidden="true" tabindex="-1"></a>Where CUDA Kernels work well and where they fail</h2><p>CUDA Kernels work well when:</p><ul><li>The same operation has to be done on a large amount of data, like matrix multiplication, image processing, and scientific simulations.</li><li>The calculations for different pieces of data do not depend on each other.</li><li>The amount of work is big enough that the time saved is more than the time spent copying data between host and device.</li></ul><p>CUDA Kernels fail or do not help when:</p><ul><li>The task is small. Copying 10 numbers to the GPU and back takes more time than adding them on the CPU. Carrying potatoes to the other room is not worth it for 10 potatoes.</li><li>The work is sequential. If step 2 needs the result of step 1, and step 3 needs the result of step 2, then thousands of threads cannot help. Only one thread can work at a time.</li><li>The threads keep taking different paths. Heavy branching causes warp divergence, and the GPU ends up doing things one by one.</li><li>The data is too big for the GPU memory. Then we have to keep moving data in and out, and the copying becomes the bottleneck.</li></ul><p>Let me tabulate the differences between CPU and GPU for your better understanding.</p><table><thead><tr><th>CPU</th><th>GPU</th></tr></thead><tbody><tr><td>Few powerful cores, let&#x27;s say 4 to 64</td><td>Thousands of small cores</td></tr><tr><td>Great at doing one task after another</td><td>Great at doing the same task on lots of data at once</td></tr><tr><td>Good for logic, decisions, and running the operating system</td><td>Good for math on big lists and tables of numbers, graphics, and AI</td></tr><tr><td>No copying needed, data is already in RAM</td><td>Data must be copied to the GPU and back</td></tr></tbody></table><p>So, we must choose between the CPU and the GPU based on our use case.</p><h2 id="summary"><a href="#summary" aria-hidden="true" tabindex="-1"></a>Summary</h2><p>Let&#x27;s summarize what we have learned.</p><ul><li>A GPU has thousands of small cores that work at the same time. It is built for doing the same operation on a lot of data.</li><li>CUDA is the platform from NVIDIA that lets us write programs for the GPU.</li><li>A CUDA Kernel is a function that runs on the GPU and is executed by thousands of threads in parallel.</li><li>We write the kernel once, for a single thread. The GPU runs it thousands of times, and each thread finds its own piece of data using <code>blockIdx</code>, <code>blockDim</code>, and <code>threadIdx</code>.</li><li>Threads are organized into blocks, and blocks are organized into a grid.</li><li>The host (CPU) and the device (GPU) have separate memory, so we allocate, copy, launch, copy back, and free.</li><li>Inside the GPU, blocks run on SMs, and threads run in warps of 32.</li><li>Global memory is big but slow, shared memory is small but fast, and registers are the fastest.</li><li>Almost every operation in an AI model is a CUDA kernel running behind the scenes.</li></ul><p>This is how CUDA Kernels work.</p><h2 id="frequently-asked-questions"><a href="#frequently-asked-questions" aria-hidden="true" tabindex="-1"></a>Frequently Asked Questions</h2><h3 id="do-we-need-to-write-cuda-code-to-use-a-gpu-with-pytorch"><a href="#do-we-need-to-write-cuda-code-to-use-a-gpu-with-pytorch" aria-hidden="true" tabindex="-1"></a>Do we need to write CUDA code to use a GPU with PyTorch?</h3><p>No. When we write <code>torch.matmul(a, b)</code> in PyTorch, we do not write any CUDA code ourselves. Behind the scenes, PyTorch calls a highly optimized CUDA Kernel written by NVIDIA, from libraries like cuBLAS, which is a collection of ready-made kernels for math operations.</p><h3 id="why-does-a-cuda-kernel-need-the-if-i--n-check"><a href="#why-does-a-cuda-kernel-need-the-if-i--n-check" aria-hidden="true" tabindex="-1"></a>Why does a CUDA Kernel need the if (i &lt; n) check?</h3><p>Because we often launch a few more threads than the number of items. The number of blocks is rounded up, so for one million numbers and 256 threads per block, we get 3907 blocks and 1,000,192 threads. The <code>if (i &lt; n)</code> check makes sure the extra threads do nothing.</p><h3 id="how-many-threads-can-one-cuda-block-have"><a href="#how-many-threads-can-one-cuda-block-have" aria-hidden="true" tabindex="-1"></a>How many threads can one CUDA block have?</h3><p>Usually up to 1024 threads. That is why we use many blocks in one kernel launch. There is no practical limit on the number of blocks, so a single kernel can run millions of threads in total.</p><h3 id="what-is-warp-divergence-in-cuda"><a href="#what-is-warp-divergence-in-cuda" aria-hidden="true" tabindex="-1"></a>What is warp divergence in CUDA?</h3><p>Warp divergence happens when threads in the same warp take different paths in an <code>if</code> condition. All 32 threads in a warp must run the same instruction, so the warp has to run both paths one after another, and this slows things down. Good CUDA Kernels keep the threads doing the same thing as much as possible.</p><h3 id="how-is-cuda-code-compiled"><a href="#how-is-cuda-code-compiled" aria-hidden="true" tabindex="-1"></a>How is CUDA code compiled?</h3><p>CUDA code is saved in a file with the <code>.cu</code> extension and compiled using <code>nvcc</code>, a special tool from NVIDIA. It understands both the normal C++ code for the host (CPU) and the kernel code for the device (GPU).</p><p>That&#x27;s it for now.</p><p>Thanks</p><p><strong>Amit Shekhar</strong><br/>Founder @ <a target="_blank" rel="noopener noreferrer" href="https://outcomeschool.com">Outcome School</a></p><p>You can connect with me on:</p><ul><li><a target="_blank" rel="noopener noreferrer" href="https://x.com/amitiitbhu">X</a></li><li><a target="_blank" rel="noopener noreferrer" href="https://www.linkedin.com/in/amit-shekhar-iitbhu">LinkedIn</a></li><li><a target="_blank" rel="noopener noreferrer" href="https://github.com/amitshekhariitbhu">GitHub</a></li></ul><p>Follow Outcome School on:</p><ul><li><a target="_blank" rel="noopener noreferrer" href="https://x.com/outcome_school">X</a></li><li><a target="_blank" rel="noopener noreferrer" href="https://youtube.com/@OutcomeSchool">YouTube</a></li><li><a target="_blank" rel="noopener noreferrer" href="https://www.linkedin.com/company/outcomeschool">LinkedIn</a></li><li><a target="_blank" rel="noopener noreferrer" href="http://github.com/OutcomeSchool">GitHub</a></li></ul><p><a target="_blank" rel="noopener noreferrer" href="https://outcomeschool.com/blog"><strong>Read all of our high-quality blogs here.</strong></a></p>
