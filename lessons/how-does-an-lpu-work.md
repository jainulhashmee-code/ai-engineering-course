I am passionate about sharing knowledge through open-source, blogs, and videos.</p><p>I teach <a target="_blank" rel="noopener noreferrer" href="https://outcomeschool.com/program/ai-and-machine-learning">AI and Machine Learning</a> at Outcome School.</p><p>Let&#x27;s get started.</p><h2 id="what-is-an-lpu"><a href="#what-is-an-lpu" aria-hidden="true" tabindex="-1"></a>What is an LPU?</h2><p><strong>An LPU is a chip that is built for one single job, running a large language model that is already trained, and producing text as fast as possible.</strong></p><p>LPU = Language Processing Unit.</p><p>In simple words, it is a processor that has been designed around the way a language model writes text, and around nothing else.</p><p>Let&#x27;s compare it with the chips that we already know.</p><ul><li>A <strong>CPU</strong> is a general worker. It can do almost anything, but it does only a few things at a time.</li><li>A <strong><a target="_blank" rel="noopener noreferrer" href="how-does-a-gpu-work-for-deep-learning.md">GPU</a></strong> is a huge team of workers. It was made for graphics, and later we found that it is also very good at the heavy parallel math that machine learning needs.</li><li>An <strong>LPU</strong> is a specialist. It was made only for running a language model that is already trained.</li></ul><p>Google took a similar specialist route with its own chip for machine learning, and we have a detailed blog on <a target="_blank" rel="noopener noreferrer" href="how-does-a-google-tpu-work.md">how a Google TPU works</a> that walks through that design step by step.</p><p>Here, two words are very important, &quot;already trained&quot;. An LPU is built for <strong><a target="_blank" rel="noopener noreferrer" href="llm-inference-optimization.md">inference</a></strong>, which means using a model that has already finished learning. It is not built for training a model.</p><p>The term LPU was introduced by a company called Groq, which builds these chips. But the ideas behind it are general, and those ideas are what we are going to understand here.</p><p>Now, the obvious question is, we already have GPUs, and they are extremely powerful, so why do we need a new chip at all?</p><p>To answer that, we must first understand what a language model actually does when it writes text. Once we understand that, the design of the LPU will feel obvious.</p><h2 id="how-an-llm-writes-text-one-token-at-a-time"><a href="#how-an-llm-writes-text-one-token-at-a-time" aria-hidden="true" tabindex="-1"></a>How an LLM writes text, one token at a time</h2><p>Before jumping into the hardware, we must know how a language model produces an answer.</p><p>A language model does not write the full answer in one shot. It writes one <strong><a target="_blank" rel="noopener noreferrer" href="tokenization-in-llms.md">token</a></strong> at a time. A token is a small piece of text, sometimes a full word, sometimes a part of a word.</p><p>Let&#x27;s say we ask the model, &quot;The capital of France is&quot;.</p><ul><li>The model reads the whole sentence and produces one token, &quot;Paris&quot;.</li><li>Now the model reads &quot;The capital of France is Paris&quot; and produces the next token, &quot;.&quot;.</li><li>Now the model reads &quot;The capital of France is Paris.&quot; and decides that the answer is over.</li></ul><p>We can write this loop like below:</p><div class="relative"><pre><code class="code-highlight">input = &quot;The capital of France is&quot;

loop:
    read the entire model
    compute the next token
    add that token to the input
    if the token means &quot;the answer is over&quot;:
        stop
</code></pre></div><p>Here, we can notice the most important thing about this loop. Every token must wait for the token before it. We cannot compute token number five before we have token number four, because token number four is part of the input for token number five.</p><p>So, text generation is a chain.</p><p>This single sentence explains almost everything about the LPU. A chain cannot be made faster by adding more workers. It can only be made faster by making each link of the chain finish quicker.</p><p>Now, let&#x27;s see what actually takes time inside one link of that chain.</p><h2 id="the-real-bottleneck-is-memory-not-math"><a href="#the-real-bottleneck-is-memory-not-math" aria-hidden="true" tabindex="-1"></a>The real bottleneck is memory, not math</h2><p>A language model is just a very large pile of numbers. These numbers are called <strong>weights</strong>, or <strong>parameters</strong>, and both words mean the same thing here. They were learned during training, and they are the entire knowledge of the model. When we hear &quot;a 70B model&quot;, it simply means a model that carries 70 billion such numbers.</p><p>Each of these numbers takes up some space. If we store each one in 8 bits, which is 1 byte, then 70 billion numbers take around 70 GB of space. So, the model itself is a 70 GB pile of numbers sitting in memory.</p><p>Storing each weight in fewer bits shrinks this pile directly, and we have a detailed blog on <a target="_blank" rel="noopener noreferrer" href="how-does-model-quantization-work.md">how Model Quantization works</a> that explains this in depth.</p><p><strong>To produce one single token, the chip must read every single weight of the model, from the first one to the last one.</strong></p><p>And what does the chip do with each weight? It multiplies it with a number and adds the result. That is one multiply and one add. That is all.</p><p>So, for every number that we move from memory into the chip, we do almost no work with it. We move a lot and we compute very less. The chip finishes the math and then sits idle, waiting for the next batch of numbers to arrive.</p><p>Let&#x27;s take an analogy for the sake of understanding.</p><p>Suppose there is a chef in a kitchen. The chef is incredibly fast and can cook any dish in a few seconds. But all the recipe books are kept in a warehouse across the road. For every single dish, the chef must walk to the warehouse, carry all the books back, read one line from each book, and cook.</p><p>The cooking takes seconds. The walking takes minutes.</p><p>Making the chef faster will not help at all. The chef is not the problem. The distance to the books is the problem.</p><p>This is exactly the situation inside a chip that is running a language model. The math is not the bottleneck. Moving the weights is the bottleneck. In simple words, the work is <strong>memory bound</strong>, not <strong>compute bound</strong>.</p><p>Now that we have understood where the time actually goes, it is time to see why a GPU has a hard time with this.</p><h2 id="why-a-gpu-struggles-here"><a href="#why-a-gpu-struggles-here" aria-hidden="true" tabindex="-1"></a>Why a GPU struggles here</h2><p>A GPU is a wonderful machine, and it is the reason modern AI exists at all. But it was designed for a different shape of problem.</p><p>A GPU keeps the model weights in a memory called <strong>HBM</strong>, which stands for High Bandwidth Memory. HBM sits right beside the chip, on the same small board, and it is genuinely fast. But it is still outside the chip, and the numbers still have to travel across a wire to reach the <strong>compute units</strong>, which are the parts of the chip that actually do the multiplying and the adding.</p><p>Before we put numbers on it, we must know one word, <strong>bandwidth</strong>. Bandwidth is simply how many bytes the memory can hand over to the chip in one second. If a memory has a bandwidth of 3 TB per second, it can deliver 3,000 GB of data every second.</p><p>Now, let&#x27;s put rough numbers on it, just for the sake of understanding.</p><div class="relative"><pre><code class="code-highlight">Weights of a 70B model, stored in 8-bit = 70 GB
Weights that must be read per token     = 70 GB

HBM bandwidth on a modern GPU           = around 3 TB per second

Time for one token  = 70 / 3000 = 0.023 seconds = 23 milliseconds
Tokens in a second  = 1 / 0.023 = around 43 tokens
</code></pre></div><p>Here, we can see that even in the perfect case, where the GPU never wastes a single moment, one token takes around 23 milliseconds, and one user gets around 43 tokens per second. That is the ceiling. No amount of extra math power will push it higher, because the wire is the limit.</p><p>So, how does a GPU cope with this today? The answer is <strong><a target="_blank" rel="noopener noreferrer" href="continuous-batching-in-llms.md">batching</a></strong>. The GPU waits for many users to arrive, and then it reads the model once and serves all of them together in the same trip. One walk to the warehouse, many dishes cooked.</p><p><strong>Advantage:</strong> The total number of tokens per second, counting all the users together, becomes very high. This total is called <strong>throughput</strong>.</p><p><strong>Disadvantage:</strong> Every individual user still waits, because their own chain of tokens is still moving at the same slow pace. And to fill a batch, the GPU sometimes has to wait for more users to show up, which adds even more delay.</p><p>So, batching gives us high throughput. It does not give us speed for one person.</p><p>There is one more thing to notice. A GPU is a flexible machine. It has caches that guess which data we will need next, schedulers that decide while running which work goes where, and waiting lines that reorder the instructions. All of this flexibility is very useful when we do not know what the program will look like. But it costs chip area, it costs power, and it makes the timing unpredictable.</p><p>So, we have two problems now. The model is too far away, and the chip spends a lot of its effort on guessing.</p><p><strong>Planning your move into AI?</strong></p><p>No matter which tech domain you work in today, with your effort, you can transition to these roles:</p><ul><li>AI Engineer</li><li>Forward Deployed Engineer</li><li>AI Agent Engineer</li><li>Harness Engineer</li><li>Voice AI Engineer</li><li>AI Architect</li><li>LLM Engineer</li><li>LLM Inference Engineer</li><li>Gen AI Engineer</li><li>MLOps Engineer</li><li>ML Engineer</li><li>Deep Learning Engineer</li></ul><p>Our <a target="_blank" rel="noopener noreferrer" href="https://outcomeschool.com/program/ai-and-machine-learning">AI and Machine Learning Program</a> at Outcome School takes you there.</p><p>The LPU attacks both of these problems directly. Let&#x27;s see how.</p><h2 id="idea-1-keep-the-model-on-the-chip"><a href="#idea-1-keep-the-model-on-the-chip" aria-hidden="true" tabindex="-1"></a>Idea 1: Keep the model on the chip</h2><p>The first idea is the simplest one to say and the hardest one to build.</p><p><strong>Do not keep the weights in a memory outside the chip. Keep them inside the chip itself.</strong></p><p>The memory that lives inside a chip is called <strong>SRAM</strong>. It sits right next to the compute units, so the numbers barely have to travel at all. Because there is no long wire and no separate memory chip to reach, SRAM is dramatically faster than HBM.</p><p>Let&#x27;s redo our calculation with on-chip memory.</p><div class="relative"><pre><code class="code-highlight">Weights that must be read per token = 70 GB

On-chip SRAM bandwidth              = around 80 TB per second

Time for one token  = 70 / 80000 = 0.000875 seconds = 0.875 milliseconds
Tokens in a second  = 1 / 0.000875 = around 1,100 tokens
</code></pre></div><p>Here, we can see that the same read now takes less than one millisecond instead of 23 milliseconds. That is roughly 26 times faster, and it turns 43 tokens per second into more than a thousand tokens per second, for a single user, without any batching at all.</p><p><strong>Note:</strong> These are rough numbers used only to show the idea. The real numbers change with the model, with how the numbers are stored, and with the hardware generation. The point to remember is the gap between the two, not the exact digits.</p><p>To feel what this means, an average person reads around 5 words per second. So a model producing a thousand tokens per second is writing far faster than any of us can read. The words stop appearing one by one and start appearing in whole paragraphs.</p><p>The chef is no longer walking across the road. The recipe books are now lying open on the kitchen counter.</p><p>This is the single biggest reason an LPU feels so fast when we watch it write.</p><p>To learn how these bandwidth numbers turn into real serving decisions - LLM Inference Bottleneck Analysis, Numbers Every AI Engineer Should Know, and designing an LLM Inference Platform - check out our <a target="_blank" rel="noopener noreferrer" href="https://outcomeschool.com/program/ai-and-machine-learning">AI and Machine Learning Program</a> at Outcome School.</p><h2 id="the-problem-with-on-chip-memory"><a href="#the-problem-with-on-chip-memory" aria-hidden="true" tabindex="-1"></a>The problem with on-chip memory</h2><p>Now, if putting the model inside the chip is such a good idea, why does everyone not do it?</p><p>Because on-chip memory is tiny.</p><p>SRAM is expensive and it takes a lot of physical space on the chip itself, and the space on a chip is the most costly thing a chip designer has. An LPU chip carries around 230 MB of it, which is a very generous amount for on-chip memory, but it is nothing compared to what a large model needs.</p><div class="relative"><pre><code class="code-highlight">Size of a 70B model in 8-bit = 70,000 MB
On-chip SRAM per LPU chip    = 230 MB

Chips needed = 70,000 / 230 = around 305 chips
</code></pre></div><p>So, one chip cannot hold the model. Not even close.</p><p>Here is the trade at the heart of the LPU. <strong>It gives up memory size to gain memory speed.</strong> A GPU chip can hold tens of GB but reads them slowly. An LPU chip holds only 230 MB but reads them incredibly fast. The LPU chose speed, and now it has to live with the consequence of that choice.</p><p>So, here comes a simple idea to the rescue. <strong>We cut the model into slices and give one slice to each chip.</strong></p><p>A language model is made of layers stacked one after the other. So, chip number 1 holds the first few layers, chip number 2 holds the next few layers, and so on, until the last chip holds the final layers. Together, the hundreds of chips hold the whole model, and every chip holds its own slice permanently, right inside itself.</p><p>Now, the next big question is, if the model is spread across 300 chips, will they not spend all their time sending data to each other?</p><p>The answer is no, and the reason is simple.</p><p>The slice of weights sitting on a chip is huge, hundreds of megabytes. But the thing that travels from one chip to the next is not the weights. It is the <strong>activation</strong>, which is the small bundle of numbers that represents the sentence so far after passing through those layers. For one token, that bundle is only a few kilobytes.</p><p>So, the huge thing stays still, and only the tiny thing moves.</p><p>This is the trade that makes the whole design work. We accept that we need many chips, and in return we never have to move the model again.</p><p>This was all about keeping the model close to the compute. Now, let&#x27;s learn about the second idea.</p><h2 id="idea-2-remove-all-the-guesswork"><a href="#idea-2-remove-all-the-guesswork" aria-hidden="true" tabindex="-1"></a>Idea 2: Remove all the guesswork</h2><p>The second idea is about the chip itself.</p><p>A normal processor decides things while it is running. It has a cache that guesses which data will be needed next. It has a branch predictor that guesses which way the program will turn. It has a scheduler that decides, while the program is running, which unit does which piece of work. All of this happens on the fly, thousands of times per second.</p><p>An LPU throws all of that away.</p><p><strong>In an LPU, the compiler decides everything before the chip is ever switched on.</strong></p><p>Here, a <strong>compiler</strong> is simply a program that takes our work and turns it into the exact instructions a chip will follow. On a normal machine, the compiler prepares the instructions and the chip still makes many decisions on its own. On an LPU, the compiler makes all of those decisions too, and it makes them in advance.</p><p>Here, one more word will help us, <strong>clock cycle</strong>. Every chip has an internal heartbeat, and each single beat is called a clock cycle. A modern chip beats more than a billion times per second, and every small action inside the chip happens on one of these beats.</p><p>Now, the compiler knows the model completely. It knows every layer, every multiplication, and every number that has to move. So it writes out a full plan that says which unit does what on which exact beat, and which piece of data sits on which wire on which exact beat.</p><p>The chip does not decide anything. It only follows the plan.</p><p>Let&#x27;s take an analogy.</p><p>Consider a busy road crossing with traffic lights. Every car arrives whenever it wants. The lights react, cars wait, some cars slip through, some get stuck. It works, but nobody can tell you exactly when a particular car will reach the other side.</p><p>Now consider a railway timetable. The train leaves at 9:00, reaches the next station at 9:14, and leaves again at 9:15. Nothing is decided in the moment. Everything was decided months ago, and the whole network is built so that the plan holds.</p><p>A GPU is the traffic crossing. An LPU is the railway timetable.</p><p>This gives us two big wins.</p><p><strong>First</strong>, all the chip space that would have gone into caches, predictors, and schedulers is now free. That space is given to more compute units and more SRAM instead. Nothing is spent on guessing.</p><p><strong>Second</strong>, the timing becomes exact. If we ask an LPU how long a request will take, it can tell us the answer down to the clock cycle, before running it. This kind of predictability is very hard to get on a normal chip.</p><p>This approach is called <strong>deterministic execution</strong>, which simply means that the same work always takes exactly the same time, because nothing is left to chance. It is also described as software-defined hardware, because the software plan is doing the job that the hardware normally does by itself.</p><p>Till now, we have learned how one chip behaves. Now, it is time to learn how hundreds of them behave together.</p><h2 id="idea-3-a-network-that-never-waits"><a href="#idea-3-a-network-that-never-waits" aria-hidden="true" tabindex="-1"></a>Idea 3: A network that never waits</h2><p>We have hundreds of chips, and each of them holds one slice of the model. Now those chips have to talk to each other for every single token.</p><p>Normally, chips talk to each other the way computers talk on a network. One chip sends a message, the other chip replies to say that it has received the message, two messages sometimes arrive at the same moment and one of them has to wait, and the waiting line sometimes gets full. Every one of these little events adds a small delay, and nobody can say in advance how big that delay will be. When the data has to pass through hundreds of chips one after the other, these small delays pile up into a big delay.</p><p>An LPU handles this differently. All the chips run on a synchronized clock, and the compiler plans the movement between chips exactly the way it plans the movement inside a chip.</p><p>So, chip number 7 knows that on cycle number 4,120 the data from chip number 6 will arrive on a particular wire. It does not ask. It does not wait. It does not check. It simply reaches out at that cycle, and the data is there.</p><p>There is no handshake, no acknowledgement, and no retry, because there is nothing to be uncertain about.</p><p>This is how the machine keeps behaving like one big chip even though it is made of hundreds of small ones.</p><p><strong>A quick note for you</strong></p><p>No matter which tech domain you work in, get familiar with these topics:</p><ul><li>LLM</li><li>RAG</li><li>MCP</li><li>Agent</li><li>Fine-tuning</li><li>Quantization</li></ul><p>We put it all together in one video:</p><p><a target="_blank" rel="noopener noreferrer" href="https://www.youtube.com/watch?v=lnfWvX66FUk">AI Engineering Explained: LLM, RAG, MCP, Agent, Fine-Tuning, and Quantization</a></p><p>No need to stop reading - bookmark it and watch later when you get time. Future you will thank you.</p><p>Now, let&#x27;s get back to the topic.</p><h2 id="the-assembly-line"><a href="#the-assembly-line" aria-hidden="true" tabindex="-1"></a>The assembly line</h2><p>Now that we have all three ideas, let&#x27;s put them together and see the machine as a whole.</p><p>Think of a car factory assembly line. Station 1 fits the frame, station 2 fits the engine, station 3 fits the doors, and so on. The car moves from station to station, and every station has its own tools kept right beside it, permanently.</p><p>A group of LPU chips working together is exactly this.</p><ul><li>Every chip is a station.</li><li>The slice of model weights is the set of tools kept permanently at that station.</li><li>The activation, that small bundle of numbers, is the car moving down the line.</li><li>The compiler is the factory schedule that says which station does what at which second.</li></ul><p>The activation enters the first chip, passes through its layers, moves to the second chip, and keeps flowing forward until it comes out of the last chip as the next token.</p><p>And here is one more advantage. The moment chip number 1 has passed its work to chip number 2, chip number 1 is free. It does not sit idle waiting for the token to finish the whole journey. It immediately starts working on the next request. So, the line always stays full, exactly like a real assembly line.</p><p>This is how hundreds of small chips behave like one very fast machine. Now, let&#x27;s walk through one actual request from start to end.</p><h2 id="what-happens-when-we-send-a-prompt"><a href="#what-happens-when-we-send-a-prompt" aria-hidden="true" tabindex="-1"></a>What happens when we send a prompt</h2><p><strong>Step 1: The model is loaded, once.</strong></p><p>Long before our request arrives, the compiler prepared the plan and the model was spread across the chips. Each chip loaded its slice into its own SRAM. This happens one time. After that, the weights never move again.</p><p><strong>Step 2: The prompt is read.</strong></p><p>We send &quot;The capital of France is&quot;. All the words of this prompt are already known, so there is no chain to wait for, and every word can be pushed through the machine together. This first stage is called <strong><a target="_blank" rel="noopener noreferrer" href="prefill-vs-decode-llm-inference-optimization.md">prefill</a></strong>.</p><p>Here, we can notice something important. Because many words travel together, one read of the weights does useful work for all of them at once. So prefill is not memory bound at all, it is compute bound, and even a GPU handles it well. We have a detailed blog on <a target="_blank" rel="noopener noreferrer" href="prefill-decode-disaggregation.md">Prefill-Decode Disaggregation</a> that explains how large serving systems use this difference to run the two phases on separate machines.</p><p><strong>Step 3: The first token is produced.</strong></p><p>The numbers flow through chip 1, chip 2, chip 3, and onward through every chip in the line. Out of the last chip comes one token, &quot;Paris&quot;. The time from our request to this first word is called <strong>time to first token</strong>, and the general word for such waiting time is <strong>latency</strong>. Lower latency means the answer starts arriving sooner.</p><p><strong>Step 4: The token is fed back in.</strong></p><p>Now &quot;Paris&quot; is added to the sentence, and the whole journey repeats to produce the next token. This stage, one token at a time, is called <strong>decode</strong>.</p><p>And decode is exactly the memory bound stage that we discussed earlier. One trip through the whole model produces only one word. This is the slow part on a GPU, and this is the part the LPU was built to fix.</p><p>There is also a software way to attack the very same problem, and we have a detailed blog on <a target="_blank" rel="noopener noreferrer" href="speculative-decoding.md">Speculative Decoding</a> that explains how a model can produce several tokens in one trip.</p><p><strong>Step 5: The loop keeps going.</strong></p><p>Every trip through the line produces exactly one token. Because the weights are already sitting inside the chips and every movement was planned in advance, each trip is extremely short. So the words appear on our screen in a smooth, fast <a target="_blank" rel="noopener noreferrer" href="how-does-token-streaming-work.md">stream</a>.</p><p><strong>Step 6: The model stops.</strong></p><p>At some point the model produces a <a target="_blank" rel="noopener noreferrer" href="stop-tokens-in-llms.md">special token that means the answer is over</a>, and the loop ends.</p><h2 id="why-an-lpu-is-fast-all-in-one-place"><a href="#why-an-lpu-is-fast-all-in-one-place" aria-hidden="true" tabindex="-1"></a>Why an LPU is fast, all in one place</h2><p>Let&#x27;s collect the reasons in one place.</p><ul><li><strong>The weights never travel.</strong> They live inside the chip in SRAM, so the slowest step of the whole process is removed.</li><li><strong>Only the small thing moves.</strong> Activations are a few kilobytes, while the weights are gigabytes.</li><li><strong>Nothing is spent on guessing.</strong> There are no caches and no predictors, so all that chip space does real work instead.</li><li><strong>The timing is planned, not discovered.</strong> The compiler knows every cycle in advance, so no unit ever waits to find out what to do next.</li><li><strong>The chips never negotiate.</strong> They share one clock, so no chip ever asks another chip whether the data is ready, and no chip ever waits in a line.</li><li><strong>The line stays full.</strong> As soon as a chip finishes its part, it starts on the next request.</li></ul><p>Put together, this is why a single user sees many hundreds of tokens per second instead of a few dozen, without waiting for any batch to fill up.</p><p>If we want to go deep into what makes inference fast - KV Cache, Paged Attention, Continuous Batching, Speculative Decoding, and vLLM - our <a target="_blank" rel="noopener noreferrer" href="https://outcomeschool.com/program/ai-and-machine-learning">AI and Machine Learning Program</a> at Outcome School covers them end to end.</p><h2 id="where-an-lpu-works-well"><a href="#where-an-lpu-works-well" aria-hidden="true" tabindex="-1"></a>Where an LPU works well</h2><ul><li><strong>Chat applications</strong>, where the answer should feel instant instead of slowly typed out.</li><li><strong><a target="_blank" rel="noopener noreferrer" href="design-a-real-time-voice-ai-agent.md">Voice assistants</a> and live translation</strong>, where a delay of even half a second is felt immediately.</li><li><strong><a target="_blank" rel="noopener noreferrer" href="ai-agent.md">AI agents</a></strong>, where the model uses a tool such as a search or a calculator, reads the result, thinks again, and uses another tool. Here the model runs many times for one single task, so every millisecond saved gets multiplied many times over.</li><li><strong><a target="_blank" rel="noopener noreferrer" href="large-reasoning-models.md">Reasoning models</a></strong>, which produce a long chain of thinking tokens before giving the final answer. A model that has to write 2,000 tokens of reasoning is exactly the case where token speed decides everything.</li><li><strong>Workloads that need predictable timing</strong>, because the compiler can tell us the exact latency in advance.</li></ul><p><strong>Stay updated:</strong> Subscribe to our <a target="_blank" rel="noopener noreferrer" href="https://outcomeschool.substack.com/subscribe">newsletter</a> to get our latest AI and Machine Learning blogs straight to your inbox.</p><h2 id="where-an-lpu-does-not-work-well"><a href="#where-an-lpu-does-not-work-well" aria-hidden="true" tabindex="-1"></a>Where an LPU does not work well</h2><p>We must also be honest about the limits.</p><ul><li><strong>It cannot train models.</strong> Training keeps changing the weights, and it also has to store a lot of extra bookkeeping numbers that record how each weight should be corrected. That needs far more memory, and the weights refuse to sit still. An LPU is built on the exact opposite assumption, that the weights never change.</li><li><strong>It needs many chips for one model.</strong> Because on-chip memory is small, a large model needs hundreds of chips before it can run at all. There is no small setup.</li><li><strong>It is not flexible.</strong> Everything is planned ahead of time. A new model, or even a change in how the numbers are stored, means the whole plan has to be built again. A GPU can accept almost anything we throw at it, right away.</li><li><strong>Long conversations put pressure on memory.</strong> While generating, the model also keeps a <strong><a target="_blank" rel="noopener noreferrer" href="kv-cache-in-llms.md">KV cache</a></strong>, which is a saved summary of everything it has already read so that it does not have to read the past again. That cache lives in the same precious on-chip memory, and it grows with the length of the conversation.</li><li><strong>Cost per token is a different question.</strong> For a job where nobody is sitting and waiting, such as reading and labelling a million documents overnight, a GPU serving a very large batch can be cheaper for the same work. There, latency does not matter at all, and only the total output matters.</li></ul><h2 id="lpu-vs-gpu"><a href="#lpu-vs-gpu" aria-hidden="true" tabindex="-1"></a>LPU vs GPU</h2><p>Let me tabulate the differences between an LPU and a GPU for your better understanding.</p><table><thead><tr><th>Point</th><th>GPU</th><th>LPU</th></tr></thead><tbody><tr><td>Built for</td><td>Any parallel math, training and inference</td><td>Running a trained language model</td></tr><tr><td>Where the weights live</td><td>HBM, next to the chip</td><td>SRAM, inside the chip</td></tr><tr><td>Memory speed</td><td>Around 3 TB per second</td><td>Around 80 TB per second</td></tr><tr><td>Memory size per chip</td><td>Tens of GB</td><td>Around 230 MB</td></tr><tr><td>Chips needed for a large model</td><td>A few</td><td>Hundreds</td></tr><tr><td>Who plans the work</td><td>The hardware, while it is running</td><td>The compiler, before it ever runs</td></tr><tr><td>Caches and branch prediction</td><td>Present</td><td>Not present</td></tr><tr><td>Chip to chip talking</td><td>Messages, with waiting and replies</td><td>One shared clock, with no waiting</td></tr><tr><td>Timing</td><td>Varies from run to run</td><td>Exact and known in advance</td></tr><tr><td>Speed for a single user</td><td>Moderate</td><td>Very high</td></tr><tr><td>Batching</td><td>Needed to get good total output</td><td>Not needed to get good speed</td></tr><tr><td>Training support</td><td>Yes</td><td>No</td></tr><tr><td>Flexibility</td><td>Very high</td><td>Low, everything is planned ahead of time</td></tr></tbody></table><h2 id="when-to-use-which-one"><a href="#when-to-use-which-one" aria-hidden="true" tabindex="-1"></a>When to use which one</h2><p><strong>Use a GPU</strong> when we are training a model, when we are experimenting and changing things often, when we need to run many different kinds of models on the same machine, or when we are running a large batch job where nobody is sitting and waiting for the output. When we do stay on the GPU, an engine like <a target="_blank" rel="noopener noreferrer" href="how-does-tensorrt-llm-work.md">TensorRT-LLM</a> squeezes out most of what that hardware can give.</p><p><strong>Use an LPU</strong> when the model is fixed and already trained, and when the speed of the answer is the thing our users actually feel. Chat, voice, agents, and reasoning models fall in this bucket.</p><p>The bigger lesson here goes beyond one chip. For years we made models faster by adding more math power. The LPU shows us that once a workload becomes memory bound, the win comes from moving data less, not from computing more. Shorten the distance between the numbers and the compute, plan every movement in advance, and the same math suddenly finishes many times faster.</p><p>Now we must have understood how an LPU works.</p><h2 id="frequently-asked-questions"><a href="#frequently-asked-questions" aria-hidden="true" tabindex="-1"></a>Frequently Asked Questions</h2><h3 id="who-created-the-lpu"><a href="#who-created-the-lpu" aria-hidden="true" tabindex="-1"></a>Who created the LPU?</h3><p>The term LPU was introduced by a company called Groq, which builds these chips. LPU stands for Language Processing Unit. The ideas behind it are general, though: keep the model weights inside the chip, let the compiler plan every step in advance, and run many chips on one shared clock.</p><h3 id="does-adding-more-compute-power-make-llm-token-generation-faster"><a href="#does-adding-more-compute-power-make-llm-token-generation-faster" aria-hidden="true" tabindex="-1"></a>Does adding more compute power make LLM token generation faster?</h3><p>No, not for one user. Generating a token is memory bound, not compute bound. To produce one token, the chip must read every weight of the model, but it does only one multiply and one add with each weight. So the chip finishes the math and waits for data, and the win comes from moving data less, not from computing more.</p><h3 id="was-the-lpu-built-to-speed-up-prefill-or-decode"><a href="#was-the-lpu-built-to-speed-up-prefill-or-decode" aria-hidden="true" tabindex="-1"></a>Was the LPU built to speed up prefill or decode?</h3><p>The LPU was built mainly to fix decode, where one trip through the whole model produces only one token. In prefill, all the words of the prompt are already known and travel together, so one read of the weights does useful work for all of them. That makes prefill compute bound, and even a GPU handles it well.</p><h3 id="doesnt-splitting-a-model-across-hundreds-of-lpu-chips-slow-it-down"><a href="#doesnt-splitting-a-model-across-hundreds-of-lpu-chips-slow-it-down" aria-hidden="true" tabindex="-1"></a>Doesn&#x27;t splitting a model across hundreds of LPU chips slow it down?</h3><p>No. The weights never move between chips. Each chip keeps its slice of the model permanently in its own SRAM. The only thing that travels from one chip to the next is the activation, which is just a few kilobytes for one token. Since all chips share one clock and follow the compiler&#x27;s plan, no chip waits for another.</p><p>That&#x27;s it for now.</p><p>Thanks</p><p><strong>Amit Shekhar</strong><br/>Founder @ <a target="_blank" rel="noopener noreferrer" href="https://outcomeschool.com">Outcome School</a></p><p>You can connect with me on:</p><ul><li><a target="_blank" rel="noopener noreferrer" href="https://x.com/amitiitbhu">X</a></li><li><a target="_blank" rel="noopener noreferrer" href="https://www.linkedin.com/in/amit-shekhar-iitbhu">LinkedIn</a></li><li><a target="_blank" rel="noopener noreferrer" href="https://github.com/amitshekhariitbhu">GitHub</a></li></ul><p>Follow Outcome School on:</p><ul><li><a target="_blank" rel="noopener noreferrer" href="https://x.com/outcome_school">X</a></li><li><a target="_blank" rel="noopener noreferrer" href="https://youtube.com/@OutcomeSchool">YouTube</a></li><li><a target="_blank" rel="noopener noreferrer" href="https://www.linkedin.com/company/outcomeschool">LinkedIn</a></li><li><a target="_blank" rel="noopener noreferrer" href="http://github.com/OutcomeSchool">GitHub</a></li></ul><p><a target="_blank" rel="noopener noreferrer" href="https://outcomeschool.com/blog"><strong>Read all of our high-quality blogs here.</strong></a></p>
