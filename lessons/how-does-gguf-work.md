We give it some text, and it gives us back some text.</p><p>Now, the natural question is, what is this model actually made of?</p><p><strong>A model is made of a huge collection of numbers called weights.</strong></p><p>In simple words, the weights are the numbers the model learned during training. When the model was trained, it read a lot of text and slowly adjusted these numbers until it became good at predicting the next word. These learned numbers are the brain of the model.</p><p>Let&#x27;s say a model has 7 billion weights. That means it is a list of 7 billion numbers. When we ask the model a question, it does a lot of math using these numbers to produce an answer.</p><p>These weights are usually stored as <strong>tensors</strong>. A tensor is just a fancy word for a grid of numbers. For the sake of understanding, we can simply think of tensors as big tables full of the model&#x27;s learned numbers. Do not worry, we do not need any math here, we only need to remember that a tensor is a block of numbers.</p><p>So, a model is basically a giant pile of numbers, the weights, arranged as tensors.</p><p>This is the foundation we needed. Now let&#x27;s understand where we want to run this model.</p><h3 id="what-is-local-inference"><a href="#what-is-local-inference" aria-hidden="true" tabindex="-1"></a>What is local inference?</h3><p>When we use the model to get an answer, that act of running the model is called <strong>inference</strong>.</p><p>In simple words, training is when the model learns, and inference is when the model is used. Inference is the model doing its job, taking our text and producing a reply.</p><p>Now, there are <a target="_blank" rel="noopener noreferrer" href="cloud-vs-on-device-model-deployment.md">two places we can run inference</a>.</p><p>The first is on a big server in the cloud, far away, owned by a company. We send our text over the internet, the server runs the model, and it sends the answer back.</p><p>The second is <strong>local inference</strong>. Local means on our own machine. So, local inference is running the model directly on our own laptop or computer, without sending anything to a far-away server.</p><p>Let&#x27;s picture both places as below:</p><div class="relative"><pre><code class="code-highlight">CLOUD INFERENCE:

  our laptop  ---- our text over internet ----&gt;  cloud server (runs model)
  our laptop  &lt;--- answer over internet --------  cloud server


LOCAL INFERENCE:

  our laptop (runs model)
     our text  ---&gt;  model  ---&gt;  answer
     nothing leaves the machine
</code></pre></div><p>Here, we can see that with cloud inference our text travels over the internet to a far-away server and the answer travels back. With local inference, everything happens on our own laptop, and nothing leaves the machine.</p><p>People want local inference for good reasons. It keeps our data private, because nothing leaves our machine. It works without the internet. And it has no per-use cost from a cloud provider.</p><p>So, our goal is clear. We want to take this giant pile of weights and run it on a normal laptop. Now let&#x27;s see why this was hard before GGUF.</p><h3 id="the-problem-before-gguf"><a href="#the-problem-before-gguf" aria-hidden="true" tabindex="-1"></a>The problem before GGUF</h3><p>To run a model on our laptop, the program needs more than just the weights. It needs a few things together:</p><ul><li>The <strong>weights</strong>, which are the model&#x27;s learned numbers, stored as tensors.</li><li>The <a target="_blank" rel="noopener noreferrer" href="tokenization-in-llms.md"><strong>tokenizer</strong></a>, which is the tool that breaks our text into small pieces the model can read, and joins the pieces back into text. We will understand this better soon.</li><li>The <strong>config and metadata</strong>, which is the information that describes the model, for example what kind of model it is, how it is built, and how much text it can handle at once.</li></ul><p>In the early days, these pieces were often scattered across many separate files in different formats. One file for the weights, other files for the tokenizer, another file for the settings. To load the model, the program had to find all of them, read each one correctly, and stitch them together.</p><p>This caused real problems:</p><ul><li><strong>It was fragile.</strong> If one file was missing or in a slightly different format, loading failed.</li><li><strong>It was not portable.</strong> Sharing a model meant sharing a folder of many files, and another person&#x27;s tool may read them differently.</li><li><strong>It was slow to load.</strong> Reading and combining many files takes time before the model is even ready.</li></ul><p>There was an earlier format called <strong>GGML</strong> that tried to pack things together for running models on normal computers. GGML was a good start and made local inference possible. But as models grew and changed, GGML had limits. It was not flexible enough, and adding new information to the file was painful. Every time the model design changed, the format struggled to keep up.</p><p>Let&#x27;s picture the old scattered way against the single-file goal as below:</p><div class="relative"><pre><code class="code-highlight">THE OLD WAY (scattered files):

  +----------------+   +------------------+   +-----------------+
  |  weights file  |   |  tokenizer file  |   |  settings file  |
  +----------------+   +------------------+   +-----------------+
          |                    |                      |
          +--------------------+----------------------+
                               |
                       program must find,
                       read, and stitch all
                       of them together

  fragile, not portable, slow to load


THE GOAL (one organized file):

  +----------------------------------------+
  |  weights + tokenizer + settings        |
  |  all packed together in one file       |
  +----------------------------------------+

  open it and run, nothing to stitch
</code></pre></div><p>Here, we can see that the old way kept the weights, the tokenizer, and the settings in separate files, so the program had to find each one, read it correctly, and stitch them together. The goal is one organized file that holds everything, so the program can open it and run right away.</p><p>We needed a single, well-organized file that holds everything, loads fast, and is easy to extend.</p><p>So, here comes GGUF to the rescue.</p><h3 id="what-is-gguf"><a href="#what-is-gguf" aria-hidden="true" tabindex="-1"></a>What is GGUF?</h3><p><strong>GGUF is a single file format that stores everything needed to run a large language model for local inference, all in one self-contained file.</strong></p><p>GGUF stands for <strong>GPT-Generated Unified Format</strong>. The key idea for us is in the words <strong>Unified Format</strong>, where &quot;Unified&quot; means everything the model needs is brought together into one single, organized file, instead of being scattered across many separate files.</p><p>In simple words, GGUF is one file that contains the model&#x27;s weights, the tokenizer, and all the settings, packed neatly together so a program can open it and start running the model right away.</p><p>It is the successor to the older GGML format. GGUF was created to fix GGML&#x27;s limits, and today it is the standard format for running models locally.</p><p>Let&#x27;s use a simple analogy. Suppose we want to move into a new house and we need a bed, a table, and a chair. The old way was like getting these as loose parts in three different boxes, with instructions in three different languages, and we had to assemble everything ourselves. GGUF is like getting one neatly packed box that has everything inside, clearly labeled, ready to use the moment we open it.</p><p>So, GGUF is the one box that holds the whole model, ready for our laptop to run.</p><p><strong>Planning your move into AI?</strong></p><p>No matter which tech domain you work in today, with your effort, you can transition to these roles:</p><ul><li>AI Engineer</li><li>Forward Deployed Engineer</li><li>AI Agent Engineer</li><li>Harness Engineer</li><li>Voice AI Engineer</li><li>AI Architect</li><li>LLM Engineer</li><li>LLM Inference Engineer</li><li>Gen AI Engineer</li><li>MLOps Engineer</li><li>ML Engineer</li><li>Deep Learning Engineer</li></ul><p>Our <a target="_blank" rel="noopener noreferrer" href="https://outcomeschool.com/program/ai-and-machine-learning">AI and Machine Learning Program</a> at Outcome School takes you there.</p><p>Now, let&#x27;s open the box and see what is inside.</p><h3 id="what-is-stored-inside-a-gguf-file"><a href="#what-is-stored-inside-a-gguf-file" aria-hidden="true" tabindex="-1"></a>What is stored inside a GGUF file?</h3><p>A GGUF file is built to hold three kinds of things together. Let&#x27;s look at each one.</p><p><strong>First, the tensors.</strong> These are the model&#x27;s weights, the learned numbers we talked about earlier. This is the biggest part of the file, because a model can have billions of numbers.</p><p><strong>Second, the key-value metadata.</strong> Metadata is data that describes other data. It is stored as simple pairs of a key and a value, like a label and its answer. For example, a key could be the architecture, which means the type of model and how it is built, and its value tells the program which kind of model this is. Another key could be the context length, which means how many tokens the model can read at once, and its value is a number like 4096. There are many such pairs that fully describe the model.</p><p><strong>Third, the tokenizer.</strong> A model cannot read raw text. It first breaks the text into small pieces called <strong>tokens</strong>. A token is a small chunk of text, roughly a word or part of a word. The tokenizer is the tool that does this splitting and also joins tokens back into text. GGUF stores the tokenizer&#x27;s vocabulary and rules right inside the file, so the program does not need any extra file to understand our text.</p><p>We have a detailed blog on <a target="_blank" rel="noopener noreferrer" href="bpe-in-llms.md">Byte Pair Encoding in LLMs</a> that explains how this tokenization step works.</p><p>Let&#x27;s picture the layout of a GGUF file as below:</p><div class="relative"><pre><code class="code-highlight">A SINGLE GGUF FILE

+--------------------------------------------------+
|  HEADER                                          |
|    marker &quot;GGUF&quot; + version + counts              |
+--------------------------------------------------+
|  KEY-VALUE METADATA                              |
|    architecture      = &quot;llama&quot;                   |
|    context length    = 4096                      |
|    tokenizer vocab   = [ ...tokens... ]          |
|    quantization info = ...                       |
+--------------------------------------------------+
|  TENSOR INFO (a small table of contents)         |
|    names, shapes, and where each tensor sits     |
+--------------------------------------------------+
|  TENSOR DATA (the weights, the big part)         |
|    [ billions of numbers, the model&#x27;s brain ]    |
+--------------------------------------------------+
</code></pre></div><p>Here, we can see that the file starts with a small <strong>header</strong>. The header begins with the four letters <code>GGUF</code>, which is a marker that tells any program &quot;this is a GGUF file&quot;. After that comes the key-value metadata, which describes the model in plain labeled pairs. Then comes a small tensor info table, which is like a table of contents that lists every tensor&#x27;s name, its shape, and where it sits in the file. Finally comes the actual tensor data, the huge block of weights.</p><p>So, with one file, the program has the weights, the description, and the tokenizer, all in one place. The problem of scattered files is solved.</p><p>Now, there is still one big challenge. These models are huge. Let&#x27;s see how GGUF helps them fit on a normal laptop.</p><h3 id="what-is-quantization"><a href="#what-is-quantization" aria-hidden="true" tabindex="-1"></a>What is quantization?</h3><p>A model with billions of weights is very large. If each weight is stored as a very detailed, very exact number, the file becomes too big to fit in a laptop&#x27;s memory.</p><p>Let&#x27;s understand the size problem with a simple idea. Each number can be stored using a certain number of <strong>bits</strong>. A bit is the smallest unit of computer memory, a single 0 or 1. The more bits we use per number, the more precise the number is, but the more space it takes.</p><p>Suppose every weight is stored using 16 bits. A model with 7 billion weights would then need about 14 gigabytes just for the weights. That is too big for many laptops to handle comfortably.</p><p>So, here comes <strong><a target="_blank" rel="noopener noreferrer" href="how-does-model-quantization-work.md">quantization</a></strong> to the rescue.</p><p><strong>Quantization is the technique of storing each weight using fewer bits, so the model becomes much smaller.</strong></p><p>In simple words, quantization means we round the model&#x27;s numbers to a simpler, shorter form that takes less space.</p><p>Let&#x27;s use a simple analogy. Suppose a price is 19.997 rupees. If we round it to 20 rupees, it is shorter and easier to store, and for most purposes it is close enough. We lost a tiny bit of exactness, but we saved space. Quantization does the same thing to the model&#x27;s weights. It stores them with fewer bits, so each number is a little less exact but takes much less room.</p><p>Let&#x27;s see the effect with numbers. If we drop from 16 bits per weight down to about 4 bits per weight, our 7 billion weight model shrinks from around 14 gigabytes to roughly 4 gigabytes. Now it fits on a normal laptop and can run on its CPU or <a target="_blank" rel="noopener noreferrer" href="how-does-a-gpu-work-for-deep-learning.md">GPU</a>.</p><p>But, here is the catch. There is a trade-off.</p><ul><li><strong>Fewer bits means smaller size and faster running, but slightly lower quality.</strong> The answers can become a little less accurate, because we made the numbers less exact.</li><li><strong>More bits means larger size and slower running, but higher quality.</strong> The answers stay closer to the original model.</li></ul><p>So, we choose the level of quantization based on our use case. If we have a small laptop and want speed, we pick a smaller form. If we have more memory and want the best quality, we pick a larger form.</p><p>GGUF supports many quantization levels, and it stores the quantized weights directly inside the file. This is one of the biggest reasons GGUF is so useful for local inference.</p><p>Quantization is one way to make a model smaller. Another is knowledge distillation, where a small model learns to copy a larger one. We have a detailed blog on <a target="_blank" rel="noopener noreferrer" href="how-does-knowledge-distillation-work.md">how Knowledge Distillation works</a> that explains this in depth.</p><p><strong>A quick note for you</strong></p><p>No matter which tech domain you work in, get familiar with these topics:</p><ul><li>LLM</li><li>RAG</li><li>MCP</li><li>Agent</li><li>Fine-tuning</li><li>Quantization</li></ul><p>We put it all together in one video:</p><p><a target="_blank" rel="noopener noreferrer" href="https://www.youtube.com/watch?v=lnfWvX66FUk">AI Engineering Explained: LLM, RAG, MCP, Agent, Fine-Tuning, and Quantization</a></p><p>No need to stop reading - bookmark it and watch later when you get time. Future you will thank you.</p><p>Now, let&#x27;s get back to the topic.</p><p>Now, these quantization levels have names that look strange at first, like <code>Q4_K_M</code>. Let&#x27;s decode them.</p><h3 id="understanding-quantization-names-like-q4_k_m"><a href="#understanding-quantization-names-like-q4_k_m" aria-hidden="true" tabindex="-1"></a>Understanding quantization names like Q4_K_M</h3><p>When we download a GGUF model, we will see names like <code>Q4_K_M</code>, <code>Q5_K_M</code>, and <code>Q8_0</code>. These look confusing, but they follow a simple pattern. Let&#x27;s break one down.</p><p>Take <code>Q4_K_M</code> as below:</p><div class="relative"><pre><code class="code-highlight">Q4_K_M
 | | |
 | | +---  M  =  the size variant (S = small, M = medium, L = large)
 | +-----  K  =  a smarter, modern quantization method
 +-------  4  =  about 4 bits used per weight
</code></pre></div><p>Here, we can see that the name has three parts. The <code>Q</code> simply means quantized. The number after it, the <code>4</code>, tells us roughly how many bits are used per weight. So <code>Q4</code> means about 4 bits per weight, and <code>Q8</code> means about 8 bits per weight. The <code>K</code> means it uses a smarter, modern method that spends bits more wisely to keep quality high. The last letter, <code>M</code>, is a size variant, where <code>S</code> is small, <code>M</code> is medium, and <code>L</code> is large.</p><p>So, the simple rule to remember is this:</p><p><strong>The number is the bits per weight. A bigger number means more bits, which means bigger file and better quality. A smaller number means fewer bits, which means smaller file and slightly lower quality.</strong></p><p>Let me tabulate the common quantization levels for your better understanding so that you can decide which one to use based on your use case.</p><table><thead><tr><th>Name</th><th>Bits per weight</th><th>File size</th><th>Quality</th><th>Good for</th></tr></thead><tbody><tr><td><code>Q4_K_M</code></td><td>about 4</td><td>smallest of these</td><td>good</td><td>laptops with limited memory, a great balance</td></tr><tr><td><code>Q5_K_M</code></td><td>about 5</td><td>medium</td><td>better</td><td>a bit more memory, slightly better answers</td></tr><tr><td><code>Q8_0</code></td><td>about 8</td><td>largest of these</td><td>best</td><td>plenty of memory, quality matters most</td></tr></tbody></table><p>Here, we can notice that <code>Q4_K_M</code> gives the smallest size with good quality, which is why it is one of the most popular choices. As we move to <code>Q5_K_M</code> and then <code>Q8_0</code>, the file gets bigger and the quality improves, but we need more memory to run it.</p><p><strong>Note:</strong> If we are not sure which one to pick, <code>Q4_K_M</code> is a safe starting point for most laptops, because it balances size and quality very well. If our answers feel a little off and we have spare memory, we can move up to <code>Q5_K_M</code> or <code>Q8_0</code>.</p><p>So, now we know how to read these names and pick the right one based on our use case.</p><p>To master Quantization and Model Compression, check out our <a target="_blank" rel="noopener noreferrer" href="https://outcomeschool.com/program/ai-and-machine-learning">AI and Machine Learning Program</a> at Outcome School.</p><h3 id="how-gguf-loads-fast-with-memory-mapping"><a href="#how-gguf-loads-fast-with-memory-mapping" aria-hidden="true" tabindex="-1"></a>How GGUF loads fast with memory mapping</h3><p>We learned that a GGUF model can still be a few gigabytes. Now the question is, how does it start so fast without filling up our memory?</p><p>The answer is a technique called <strong>memory mapping</strong>, often written as <strong>mmap</strong>.</p><p>Let&#x27;s first understand the slow way. The simple way to load a file is to read the whole thing from the disk into memory before we use it. For a 4 gigabyte model, that means waiting until all 4 gigabytes are copied into memory. That is slow, and it uses a lot of memory right away.</p><p>So, here comes memory mapping to the rescue.</p><p><strong>Memory mapping lets the program treat the file on disk as if it were already in memory, without copying the whole thing first.</strong></p><p>In simple words, instead of loading everything up front, the program only reads the parts of the file it actually needs, exactly when it needs them.</p><p>Let&#x27;s use a simple analogy. Suppose we have a thick book. The slow way is to photocopy the entire book before reading a single page. Memory mapping is like keeping the book on the table and simply opening the exact page we need, only when we need it. We do not copy the whole book first. We just read pages on demand.</p><p>Let&#x27;s see the difference as below:</p><div class="relative"><pre><code class="code-highlight">WITHOUT memory mapping:

  disk file (4 GB)  ===&gt; copy all 4 GB into memory ===&gt; then start
       slow start, uses a lot of memory immediately


WITH memory mapping (GGUF):

  disk file (4 GB)  --- start immediately ---&gt;
       the program reads only the needed parts, when needed
       fast start, memory used efficiently
</code></pre></div><p>Here, we can see that without memory mapping the program must copy all 4 gigabytes before it even starts, which is slow and heavy on memory. With memory mapping, the program starts right away and pulls in only the parts of the model it needs, when it needs them. This is why a GGUF model can start so quickly.</p><p>GGUF is designed to work perfectly with memory mapping. Because the tensors are laid out in a clean, ordered way inside the file, the program can jump straight to any tensor it needs and read it directly. The model starts fast and uses memory efficiently.</p><p>This is how GGUF gives us a fast startup on a normal machine.</p><p>If we want to go deep into LLM Inference Engineering and Cloud vs On-device Deployment, we have a complete program on it - check out our <a target="_blank" rel="noopener noreferrer" href="https://outcomeschool.com/program/ai-and-machine-learning">AI and Machine Learning Program</a> at Outcome School.</p><h3 id="why-gguf-is-cross-platform-and-extensible"><a href="#why-gguf-is-cross-platform-and-extensible" aria-hidden="true" tabindex="-1"></a>Why GGUF is cross-platform and extensible</h3><p>There are two more qualities of GGUF that make it so widely used. Let&#x27;s understand both.</p><p><strong>First, GGUF is cross-platform.</strong> Cross-platform means it works the same way across different operating systems and devices. The same GGUF file runs on Windows, macOS, and Linux, and on different kinds of processors. We do not need a different file for each system. We download one GGUF file and it just works wherever we run it.</p><p><strong>Second, GGUF is extensible.</strong> Extensible means it is easy to add new information to the format without breaking older files. Remember, the metadata inside GGUF is stored as simple key-value pairs. So, when a new kind of model needs a new setting, the format simply adds a new key-value pair. Old programs can still read the file, and new programs can read the new key. This is exactly the weakness that the older GGML format had, and GGUF fixed it.</p><p>So, GGUF is portable across machines and flexible enough to grow with new models. This is why it became the standard.</p><p><strong>Stay updated:</strong> Subscribe to our <a target="_blank" rel="noopener noreferrer" href="https://outcomeschool.substack.com/subscribe">newsletter</a> to get our latest AI and Machine Learning blogs straight to your inbox.</p><p>Now, let&#x27;s see where GGUF is actually used.</p><h3 id="gguf-in-the-real-world"><a href="#gguf-in-the-real-world" aria-hidden="true" tabindex="-1"></a>GGUF in the real world</h3><p>GGUF is the format used by <strong><a target="_blank" rel="noopener noreferrer" href="how-does-llama-cpp-run-llms-on-everyday-hardware.md">llama.cpp</a></strong> and the popular tools built on top of it.</p><p>Let&#x27;s understand <code>llama.cpp</code> first. It is an open-source program written to run large language models efficiently on normal computers, including laptops, using the CPU or the GPU. It is fast, lightweight, and it reads models in the GGUF format. GGUF was created as part of this <code>llama.cpp</code> world to be the clean, single-file format these models use.</p><p>Many friendly tools are built on top of <code>llama.cpp</code>, and they all use GGUF:</p><ul><li><strong><a target="_blank" rel="noopener noreferrer" href="how-does-ollama-work.md">Ollama</a>.</strong> This is a tool that lets us download and run models locally with a simple command. Under the hood, it uses GGUF files and <code>llama.cpp</code>.</li><li><strong>LM Studio.</strong> This is a desktop app with a nice screen where we can search for models, download GGUF files, and chat with them, all on our own machine.</li></ul><p>Let&#x27;s picture how these pieces stack together as below:</p><div class="relative"><pre><code class="code-highlight">  +-----------------+        +-----------------+
  |     Ollama      |        |    LM Studio    |   the friendly tools we use
  +-----------------+        +-----------------+
            |                         |
            +------------+------------+
                         |
                +------------------+
                |    llama.cpp     |   runs the model efficiently
                +------------------+
                         |
                +------------------+
                |  .gguf file      |   weights + tokenizer + metadata
                +------------------+
</code></pre></div><p>Here, we can see that the GGUF file sits at the bottom holding everything the model needs. The <code>llama.cpp</code> program reads that file and runs the model. The friendly tools like Ollama and LM Studio sit on top of <code>llama.cpp</code>, giving us a simple way to use it. So they all rely on the same single GGUF file underneath.</p><p>In all of these, the flow is the same. We download a single file that ends with <code>.gguf</code> for the model and the quantization level we want, the tool opens it using memory mapping, reads the weights, the tokenizer, and the metadata from that one file, and we start chatting. There is nothing to assemble and no scattered files to manage.</p><p>So, anywhere we want to run a large language model on our own machine, GGUF is very likely the format we will use.</p><p>The models we run locally like this are often Small Language Models, compact enough to fit on a laptop or phone. We have a detailed blog on <a target="_blank" rel="noopener noreferrer" href="small-language-models-slms.md">Small Language Models (SLMs)</a> that explains why smaller models matter.</p><p>This is how GGUF works. It packs the model&#x27;s weights, its tokenizer, and its metadata into one self-contained file, it uses quantization to shrink the weights so big models fit on a normal laptop, and it loads quickly with memory mapping, which is why it became the standard format for running large language models locally.</p><h2 id="frequently-asked-questions"><a href="#frequently-asked-questions" aria-hidden="true" tabindex="-1"></a>Frequently Asked Questions</h2><h3 id="what-is-the-difference-between-gguf-and-ggml"><a href="#what-is-the-difference-between-gguf-and-ggml" aria-hidden="true" tabindex="-1"></a>What is the difference between GGUF and GGML?</h3><p>GGUF is the successor to the older GGML format. GGML made local inference possible, but it was not flexible enough, and adding new information to the file was painful. GGUF fixed this by storing metadata as simple key-value pairs, so new settings can be added without breaking older files.</p><h3 id="which-gguf-quantization-level-should-we-pick"><a href="#which-gguf-quantization-level-should-we-pick" aria-hidden="true" tabindex="-1"></a>Which GGUF quantization level should we pick?</h3><p><code>Q4_K_M</code> is a safe starting point for most laptops, because it balances size and quality very well. If the answers feel a little off and we have spare memory, we can move up to <code>Q5_K_M</code> or <code>Q8_0</code>. A bigger number means a bigger file and better quality.</p><h3 id="does-a-quantized-gguf-model-give-worse-answers"><a href="#does-a-quantized-gguf-model-give-worse-answers" aria-hidden="true" tabindex="-1"></a>Does a quantized GGUF model give worse answers?</h3><p>Slightly. Fewer bits per weight make the numbers a little less exact, so the answers can become a little less accurate. In return, the model becomes much smaller and faster. With more bits, the file is larger but the answers stay closer to the original model.</p><h3 id="do-we-need-separate-tokenizer-files-to-run-a-gguf-model"><a href="#do-we-need-separate-tokenizer-files-to-run-a-gguf-model" aria-hidden="true" tabindex="-1"></a>Do we need separate tokenizer files to run a GGUF model?</h3><p>No. GGUF stores the tokenizer&#x27;s vocabulary and rules right inside the file, along with the weights and the metadata. So the program does not need any extra file to understand our text. We download a single <code>.gguf</code> file and start running the model.</p><h3 id="do-ollama-and-lm-studio-use-gguf"><a href="#do-ollama-and-lm-studio-use-gguf" aria-hidden="true" tabindex="-1"></a>Do Ollama and LM Studio use GGUF?</h3><p>Yes. Both Ollama and LM Studio are built on top of <code>llama.cpp</code>, and they use GGUF files. The GGUF file holds everything the model needs, <code>llama.cpp</code> reads it and runs the model, and these tools give us a simple way to use it.</p><p>That&#x27;s it for now.</p><p>Thanks</p><p><strong>Amit Shekhar</strong><br/>Founder @ <a target="_blank" rel="noopener noreferrer" href="https://outcomeschool.com">Outcome School</a></p><p>You can connect with me on:</p><ul><li><a target="_blank" rel="noopener noreferrer" href="https://x.com/amitiitbhu">X</a></li><li><a target="_blank" rel="noopener noreferrer" href="https://www.linkedin.com/in/amit-shekhar-iitbhu">LinkedIn</a></li><li><a target="_blank" rel="noopener noreferrer" href="https://github.com/amitshekhariitbhu">GitHub</a></li></ul><p>Follow Outcome School on:</p><ul><li><a target="_blank" rel="noopener noreferrer" href="https://x.com/outcome_school">X</a></li><li><a target="_blank" rel="noopener noreferrer" href="https://youtube.com/@OutcomeSchool">YouTube</a></li><li><a target="_blank" rel="noopener noreferrer" href="https://www.linkedin.com/company/outcomeschool">LinkedIn</a></li><li><a target="_blank" rel="noopener noreferrer" href="https://github.com/OutcomeSchool">GitHub</a></li></ul><p><a target="_blank" rel="noopener noreferrer" href="https://outcomeschool.com/blog"><strong>Read all of our high-quality blogs here.</strong></a></p>
